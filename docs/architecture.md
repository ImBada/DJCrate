# DJCrate 구조와 설계 결정

코드 위치보다 **왜 이렇게 만들었는지**를 적는다. 파일별 설명은 코드와 `AGENTS.md`의 구조 목록을 본다.

## 모듈

```
DJCrate · DJCrate(CLI)
   ├─▶ DJCStorage ──▶ RekordboxKit ──▶ DJCDomain
   └─▶ DJCAnalysis ─────────────────▶ DJCDomain
```

- **DJCDomain**: 입출력 없는 규칙. 큐 편집(메모리 큐 한도·같은 자리·활성 루프 하나), 루프 길이·끝, 그리드 따라가기, 게인 정책, 재생 예약(`PlaybackSchedule`·`LoopPlanner`·재생 퀀타이즈 `PlayQuantize`·`JumpPlanner`). 테스트가 가장 빠르고 촘촘한 곳이다.
- **RekordboxKit**: rekordbox 형식을 아는 유일한 곳. DB 열기, ANLZ 읽기·쓰기, 스냅샷, 쓰기·백업·되돌리기, 쓰기 전 확인.
- **DJCStorage**: DJCrate 자신의 파일(초안·추가한 곡·반영 묶음). rekordbox 쓰기 모듈은 이 경로를 모른다(백업 폴더를 인자로 받는다).
- **DJCAnalysis**: 소리 분석과 곡 편집 렌더. rekordbox를 모른다(시간축 차이는 인자로 받는다).
- **DJCrate**: 화면 모델은 바깥을 주입받는다. 덱은 `DeckAudioEngine`(오디오)·`DeckStorage`(초안·설정), 반영 흐름은 `ReflectionHost`(라이브러리)·`ReflectionPrompter`(확인 창). 시험에서는 가짜로 바꾼다.

## 테스트

- 순서: 실패하는 테스트 → 구현 → `scripts/check.sh`(쓰기 80%, 코어 60% 줄 커버리지 목표).
- rekordbox 쓰기는 실제 라이브러리 없이 시험한다. `Tests/Support/Resources/rekordbox-7.2.18-schema.sql`은 실제 DB에서 **구조만** 뽑은 것(`djc schema-dump`, 데이터 0행)이고, 같은 키로 암호화해 픽스처 DB를 만든다. 분석 파일·음원도 합성한다.
- 골든 테스트는 rekordbox 실험에서 확인한 칸 값을 그대로 기대값으로 둔다(실험 곡·날짜를 주석으로).
- 소리·실제 화면은 단위 테스트로 못 잡는 부분만 디버그 빌드의 자가 테스트로 본다(`AGENTS.md`의 표).
- 시험은 걸린 시간으로 판정하지 않는다(#149·#153·#154). "N초 안에 끝남" 대신 순서·상태·신호로 판정하고, 기다릴 때는 `waitForState`(`Tests/DJCrateTests/StateWaiting.swift`)로 상태를 기다린다. 그 안전망(300초)은 판정이 오지 않는 잘못된 구현에서 시험이 멈추지 않게 할 뿐이다. 실제 마우스·키 상태처럼 시험 밖 상태를 읽는 곳은 주입해 시험이 정한다(`TrackListCoordinator.isMouseDown`). 부하 재현은 `yes`를 여러 개 띄우고 DJCrateTests 전체를 한 프로세스로 돌린다(필터로 좁히면 다른 `@MainActor` 시험과 메인 액터를 나눠 쓰는 정체가 없어 재현되지 않는다).
- SQLCipher는 프로세스에서 처음 쓰는 순간 여러 스레드가 겹치면 전역 초기화가 끝나기 전에 들어온 스레드가 `PRAGMA key`에서 "sqlcipher not initialized"로 실패한다(4.7 이후 초기화 경쟁). DB는 `CipherDatabase`로만 열어 `sqlite3_initialize`를 한 번 거치게 한다. 새 프로세스에서 처음 여는 경쟁은 `djc lab cipher-cold-open`이 만든다(`Tests/djcTests/CipherColdOpenTests`).

## 데이터 흐름

```
rekordbox master.db ──(스냅샷 사본)──▶ RekordboxLibrary ──▶ LibraryStore(목록·필터) ──▶ DeckModel(덱)
        ▲                                                         │
        │                                            편집은 초안으로 쌓임
        │                  CueDraft · GridDraft · 게인 초안 · TagDraft · ArtworkDraft · PlaylistDraft
        │                                                         │
        └──── RekordboxWriter / RekordboxGridWriter ◀── rekordbox에 쓰기(rekordbox 꺼져 있을 때만)

새 곡 ── StagedTrack ──┬── RekordboxTrackWriter ──▶ 컬렉션에 직접 넣기(rekordbox 꺼져 있을 때만)
                      └── RekordboxXML ──▶ XML 만들기 ──▶ 사용자가 rekordbox에서 Import To Collection
기존 곡의 큐·그리드 초안 ── Reflection ──▶ XML 만들기 ──▶ 사용자가 rekordbox에서 Import To Collection
```

- **XML은 별도의 호환 경로다.** 기존 곡은 `Reflection.plan`으로 큐·그리드 변경과 옮길 수 없는 정보를 확인하고, `Reflection.document`로 내보낸다. 새 곡은 `RekordboxXML.document`로 곡 정보·그리드·점 큐를 내보낸다. 두 경로는 같은 연동 파일을 덮어쓰되 재생 목록 이름은 각각 `DJCrate 반영`·`DJCrate 추가`로 유지한다. 새 스냅샷에서 기존 곡은 `Reflection.verify`로 큐·그리드·곡 정보를, 새 곡은 `StagedTrack.ImportCheck`로 그리드를 비교한다. 태그·게인·재생 목록 초안까지 다루는 직접 쓰기와 범위가 같지 않으며 전체 라이브러리 입출력도 아니다([지원 범위와 사용법](../README.md#xml-호환-경로)).
- **라이브러리 전체 XML 내보내기는 읽기만 하는 세 번째 경로다(#72).** `RekordboxLibraryXML`이 스냅샷(`RekordboxLibrary`)과 분석 파일(PQTZ)을 읽어 COLLECTION·PLAYLISTS를 쓰고 지정한 출력 파일 하나에만 쓴다(앱 "라이브러리 XML 내보내기…"·`djc xml-export`). 위 두 경로의 출력은 바꾸지 않고 `RekordboxXML`의 직렬화 도우미(`escape`·`location`·`kind`)만 나눠 쓴다. 쓰지 않은 초안은 읽지 않으며, 시각은 DB·분석 파일이 이미 rekordbox 시간축이라 인코더 지연을 따로 더하지 않는다. 출력은 `.xml`만 받고 rekordbox 폴더·USB의 `PIONEER/`·DJCrate 데이터 폴더(백업 포함)·연동 XML 자리는 `checkOutput`이 거부한다. 넣지 않는 칸은 `docs/cli.md`에 있다.
- **목록 선택과 덱은 따로다(#93).** 목록 한 번 클릭·↑↓·태그 시트 커서는 고른 곡(`LibraryStore.selection`)만 바꾸고 덱은 그대로다. 덱은 불러오기 명령(`LibraryStore.loadToDeck`: 더블클릭(키를 고칠 수 있는 곡의 키 칸은 키 고르기, #204)·⌘→·오른쪽 클릭 "덱에 불러오기"·덱으로 끌어다 놓기)으로만 바뀐다. 재생 기록의 반복 행도 컬렉션 곡으로 올리고(`deckTrackID` = ContentID), 스냅샷을 새로 읽으면 덱의 곡만 새 값으로 맞추거나 지워졌으면 내린다. 곡을 추가해도 덱은 그대로고, 덱의 곡을 편집해 렌더한 편집본과 덱에 올린 추가한 곡을 rekordbox에 넣은 경우만 덱을 바꿔 올린다.
- **읽기는 사본에서만.** 라이브 DB를 열어 두면 rekordbox와 잠금·WAL이 얽힌다. `LibrarySnapshot`이 사본을 뜨고, rekordbox가 켜져 있으면 `--force`일 때만 WAL까지 합친 읽기용 사본을 뜬다.
- **편집은 초안.** 초안은 JSON으로 `~/Library/Application Support/DJCrate/`에 저장된다. 앱을 꺼도 남고, 반영하면 지운다. 초안마다 만들 때의 rekordbox 상태(`base`)가 있어서, 그 뒤 rekordbox에서 바뀐 곡은 쓰지 않는다(덮어쓰기 방지).
- **명시적 동기화는 초안을 보존한다(#159).** 툴바·⌘R의 `rekordbox와 동기화`는 기존 읽기용 사본 경로를 쓰며, `--db`·`DJC_DB` 모드에서는 지정 사본만 다시 읽는다. 태그의 안 고친 칸은 최신값으로 합치고 같은 칸이나 앨범 관계가 충돌하면 초안을 보존해 인스펙터에서 칸별로 선택한다. 큐·그리드 초안의 기준은 자동으로 덮지 않는다. 쓰기·미저장 덱 편집 중에는 동기화하지 않고, 읽는 동안 쓰기가 시작되면 결과를 버린다. 태그 저장 실패는 메모리 입력·삭제 의도를 보존하고 명시적 동기화나 쓰기 준비에서 실패한 저장만 재시도한다.
- **재생 목록 초안은 편집 순서다.** 곡 초안과 달리 편집끼리 기대므로(새로 만든 목록에 곡 넣기, 넣은 뒤 옮기기) `PlaylistDraft`는 `PlaylistEdit`을 적힌 순서대로 들고, 편집마다 기대는 rekordbox 목록의 처음 상태(`base`)를 적는다. 사이드바·곡 목록은 rekordbox 상태에 초안을 얹은 모양(`PlaylistLayout`, 쓰기 모듈과 같은 규칙)을 보여 준다. 쓰기 모듈은 트랜잭션 안에서 base와 지금 상태를 비교해 바뀐 목록의 편집만 막고, 앱은 쓴 편집만 초안에서 뺀다. 되돌리면 그때 쓴 편집을 되돌린 상태에 다시 쌓는다.
- **반영 흐름**은 `ReflectionCoordinator` 한 곳이다: rekordbox 꺼짐 확인 → 스냅샷 사본으로 끝까지 써 보고 되돌림(미리 보기) → 확인 창 → 쓸 수 있는 것만 실제로 쓰기 → 토스트. 쓰는 동안 덱은 재생을 멈추고 조작을 막는다.
- **반영 뒤에는 조용히 다시 읽는다.** 화면을 로딩으로 바꾸지 않고 스냅샷을 새로 떠서 목록을 바꾸고, 덱은 소리·파형·분석을 그대로 둔 채 초안·그리드·게인만 새 값으로 맞춘다(`DeckModel.softReload`).
- **쓰기 완료는 Music 조회를 기다리지 않는다(#130).** 쓰기·복원·곡 추가·삭제 뒤에는 새 DB와 같은 출처의 기존 iTunes 사본을 결합해 새 스냅샷 옆에도 보존한다. 현재 동기화 선택과 일치하는 정상 사본을 이전 자료보다 우선하고, 캐시가 없을 때는 읽기 실패 안내를 유지한다. 스냅샷 대기열은 DB 복사·읽기만 직렬화한다. Music 캡처는 대기열 밖에서 수행하고 이미 읽은 곡 목록에 결합하며, 요청 세대와 사본별 순서를 검사해 늦은 결과를 버린다. 다만 쓰기 뒤 다시 읽기가 버린 Music 조회는 다시 조회하지 않고 새 사본에서 그 결과를 이어받는다(지난 세션 목록이 세션 내내 남지 않게). 수동 새로고침은 해당 Music 작업까지 기다리되 뒤따르는 쓰기를 막지 않는다. DB 읽기·Music 캡처·iTunes 사본 적용·곡 목록 준비는 단계별로 시간을 남긴다. Framework 캡처는 동기화 선택 창에 필요한 전체 목록을 유지하되 곡 위치(없는 위치 포함)는 영구 ID별로 한 번만 조회하며, 다음 캡처에는 캐시를 넘기지 않는다.
- **iTunes 선택 창은 이미 읽은 전체 목록을 재사용한다.** 현재 동기화 선택과 일치하는 정상 카탈로그가 있으면 Music 응답을 기다리지 않고 창을 연다. 앱을 켤 때도 이 캐시가 있으면 DB와 화면을 먼저 준비하고 Music 최신화는 뒤에서 진행한다. 최신화가 도는 동안 창은 캐시를 보여 주되 동기화(쓰기)는 막고, 끝나면 그 결과로 다시 연다(낡은 폴더 계층으로 `playlists3.sync`를 쓰지 않게). 창의 새로고침은 카탈로그를 다시 읽으며, 겹친 요청은 한 캡처를 공유한다. 갱신 실패 때는 이전 자료와 편집한 선택을 보존하고, 더 최신 라이브러리나 다른 DB의 상태를 오래된 결과로 덮지 않는다. 명시한 사본 모드에서는 새로고침도 Music에 접근하지 않는다.
- **되돌리기.** 쓰기 전 전체 백업(`rekordbox-backups/<시각>-write/`)에 그때 쓴 초안도 함께 넣어 두고, 되돌리면 DB·분석 파일을 복원하고 초안을 다시 살린다.

## 시간축

rekordbox는 압축 음원 앞의 인코더 지연을 잘라 내지 않는다. 그래서 rekordbox의 0초는 AVFoundation의 0초보다 앞선다.

- 덱·초안·그리드의 모든 시각 = **rekordbox 시간축**(음원 시각 + `RekordboxTimeline.predictedOffset`).
- 음원을 읽을 때(재생 프레임 선택)와 파형을 그릴 때만 `timelineOffset`만큼 뺀다.
- 150곡 실측으로 맞췄고, 내보낸 그리드가 rekordbox 그리드와 1ms 안에서 일치한다.

## 분석

| 기능 | 방법 | 수준 |
|---|---|---|
| 섹션·메모리 큐 제안 | Apple Music Understanding 섹션 경계 → 박에 맞춤 | 직접 찍은 큐 ±1박 재현율 62% |
| 그리드 추정 | MU 박·마디 + 1ms 어택 곡선, 105~215 BPM, 구간별 맞춤(변속) | BPM ±0.05 84%, 박 일치 67% |
| 조성 흐름 | 16384점 FFT 크로마 + 라이브러리 400곡으로 학습한 프로필 + 12조표 비터비 | 주 조표 rekordbox 일치 67% |
| 음량 | BS.1770 통합 음량(vDSP K-가중) | ffmpeg ebur128과 ±0.05 LU |

- 결과는 `analysis/`에 캐시한다(파일이 바뀌면 다시 계산).
- 오토게인은 rekordbox 값(약 −10 LUFS 기준)을 기본으로 쓰고, DJCrate가 잰 음량과 1.5dB 넘게 다르면 제안한다.
- 게인·그리드·키 제안은 덱 제안 줄(`DeckSuggestionBar`) 한 곳에 모은다. 문구는 `DeckSuggestion`(이름 · 값 · [적용] [무시]) 한 규칙이고, 게인·그리드는 덱 초안, 키는 태그 초안(`LibraryStore`)이 된다. 무시 표시는 종류마다 따로 저장하지만(`SettingKeys` 하단) 되살리기는 "무시한 제안 다시 보기" 하나다.

## 덱 오디오 (`DeckAudio`)

```
trackNode → gainUnit(오토게인) → trackMixer(볼륨) ┐
clickNode(메트로놈) ─────────────────────────────┴→ subMixer → varispeed → timePitch → 출력
```

- 곡은 불러올 때 메모리에 통째로 디코딩해 둔다(20분 이하). 재생·점프·CUE가 외장 드라이브에서도 바로 반응한다. 디코딩이 끝나기 전에는 파일에서 읽는다.
- **`pause()` 금지, `stop()`만.** pause 뒤 다시 켜면 `play(at:)`의 호스트 시각이 쉬기 전 기준으로 환산돼, 쉰 시간만큼 소리가 늦고 무음이 쌓였다.
- **엔진은 메인 스레드 밖에서 만든다(#142).** 출력 장치 IO 유닛을 여는 `mainMixerNode`·`outputNode`는 coreaudiod가 응답하지 않으면 끝없이 기다려, 메인 스레드에서 부르면 앱이 첫 화면 전에 멈췄다. 엔진·노드 묶음(`DeckAudioGraph`, 편집 창은 `EditAudioGraph`)은 직렬 큐(`AudioEngineQueue`)에서 만들고 다 만든 뒤에만 메인 액터로 넘긴다(넘긴 뒤에는 메인 액터만 만진다). 넘겨받기 전에도 곡은 불러 두고, 재생만 "오디오 장치를 쓸 수 없습니다" 안내와 함께 막으며 다시 준비를 시도한다.
- **루프는 샘플 단위.** 재생 노드에 "조각"(노드 샘플 → 곡 프레임, 루프 길이)을 예약해 오디오가 직접 되풀이한다. 화면 틱이 되돌리던 예전 방식은 바퀴마다 짧게 끊겼다.
  - 오프라인 렌더 실험으로 확인한 제약:
    - 시각을 정한 `.interrupts` 예약은 이미 그린 곳보다 렌더 블록 하나 이상 앞서야 정확하다.
    - 앞서 예약하면 되풀이(`.loops`) 버퍼도 바퀴 중간에서 샘플 단위로 끊긴다(렌더 블록 441·512·1024 확인). 처음에는 "바퀴 경계에서만"이라고 잘못 결론 내려 ½이 한 바퀴 늦게 적용됐다.
    - `.interrupts` 버퍼 뒤에 시각 없이 줄 세운 버퍼는 지워진다.
    - 나중에 예약한 `.interrupts` 버퍼는 그 시각에 앞서 예약한 미래 버퍼(루프 몸통 포함)를 모두 지우고, 같은 시각이면 나중 것이 이긴다(2026-09-27).
    - 재생 시작 버퍼도 노드 샘플 0에 시각을 정해 예약한다. 시각 없이(nil) 두면 다음 렌더 덩어리에서 시작해 노드 시각과 곡 프레임이 최대 한 덩어리 어긋났고, 그만큼 첫 루프·점프가 일찍 넘어갔다(2026-09-27 실측, `--jump-audio-selftest`).
  - 무엇을 언제 예약할지(걸기·길이 바꾸기·나가기, 늘일 때 다리 버퍼)는 `LoopPlanner`가 순수 함수로 정하고, `DeckAudio`는 그 계획을 실행만 한다.
  - 곡 위치·메트로놈 클릭도 이 조각을 따라 계산한다(`PlaybackSchedule`). 클릭 예약 창은 반열린 구간 `[from, to)`라 창 경계의 박이 빠지거나 두 번 나지 않는다.
- **재생 퀀타이즈(Q, #90·#107).** 재생 중 핫큐는 현재 박을 계속 재생하다 다음 정수 비트그리드 선에서 저장 큐의 첫 샘플로 넘어간다. 이전 1/4·1/2·1박 저장값은 호환용으로만 읽으며 모두 같은 동작이다. 큐 앞부분에 source의 소수 박을 더하지 않는다. 경계·착지는 `PlayQuantize`, 예약은 `JumpPlanner`가 루프와 같은 방식(시각을 정한 `.interrupts`)으로 정한다. 이미 렌더한 노드 위치에서 실제 출력 버퍼 두 개만큼 여유를 두고 예약 가능한 첫 경계를 쓴다(이미 렌더됐거나 안전한 예약 여유 안의 경계는 소급 변경할 수 없어 그다음 큰 박을 쓴다). 착지는 곡 시각 비교 대신 노드 경계 도달 여부로 확인한다. 넘어가기 전에 다른 핫큐를 누르면 새 점프가 그 자리를 대신하며, 새 예약을 못 하면 옛 예약도 취소하고 화면 틱으로 넘긴다. 일시정지·스크럽으로 예약을 취소하면 도착 전 루프 상태를 복원한다. 새 루프 조작도 대기 중 점프를 취소하고 현재 재생 구간에 적용한다. 메트로놈은 옛 선예약을 지우고 새 시간표로 다시 예약해 점프 뒤의 박·강박을 따른다. 곡을 메모리에 풀기 전에는 화면 틱이 경계를 지날 때 넘긴다. 이 대체 경로는 늦은 틱만큼 큐 뒤에서 시작해 박자 지연을 보상하므로, 샘플 예약 경로처럼 큐의 첫 샘플과 정확한 경계를 보장하지 않는다.
- **끄는 중 핫큐(#133).** 마우스를 쥔 SwiftUI 제스처(`DragGesture`·`MagnifyGesture`)가 도는 동안 AppKit은 이벤트 추적 모드로 이벤트를 받고, 그 사이 키 이벤트는 `sendEvent`에 가지 않고 버려진다(로컬 모니터인 `KeyRouter`까지 오지 않는다, 2026-09-28 최소 SwiftUI 앱 실험). 그래서 확대 파형을 끄는 동안에만 `DragHotCueKeys`가 핫큐 키의 눌림 상태를 8ms마다 읽어 새로 누른 키만 보낸다(`HotCueKeyWatch`, 끌기 전부터 누르던 키는 무시). 빈 칸은 끄는 중 자리에 찍고, 저장된 칸은 자리만 옮기며 끌기 기준점(`ScrubAnchor`)도 옮겨 다음 끌기가 거기서 이어진다. 재생·루프는 놓은 뒤 평소대로 한다(끄는 중에 재생을 시작하면 끌기와 부딪친다).
- 템포는 키 락이면 timePitch, 아니면 varispeed. 클릭도 같은 경로를 지나 템포를 바꿔도 박에 붙어 있다.

## 곡 편집 (`TrackEdit`, #80 PoC)

원본 마디 구간을 차례로 이어 새 WAV·AIFF로 렌더하고, 그리드·큐를 옮겨 새 곡으로 넣는다. 원본 음원은 읽기만 한다. 무엇을 어디에 쓸지는 `TrackEdit`(순수)가 정하고 `EditRenderer`는 그대로 읽고 쓴다. 실험 명령은 `djc lab edit-render`.

- **조각은 온전한 마디만.** 그래야 출력 그리드가 원본 BPM의 한 구간으로 이어진다. 곡 머리(0마디, 첫 다운비트 앞)는 맨 앞에만, 곡 끝에서 잘린 마지막 마디는 맨 뒤에만 둔다. 템포 구간이 여러 개인 곡은 막는다. 원본에서 이어지는 구간(`1-16,17-64`)은 한 조각으로 합친다(이음새가 아니다).
- **어긋남이 쌓이지 않게.** 출력 시각은 앞 조각 마디 수 × 마디 길이로 바로 구하고, 프레임은 경계마다 반올림한다(1마디 200번 이어도 k번째 조각은 k × 마디 길이 자리).
- **이음새는 4ms 섞기, 이음새 앞에서.** 앞 조각 끝을 줄이며 다음 조각 바로 앞 원본을 키워 이음새에서 끝낸다. 다음 조각의 다운비트 어택은 그대로다.
- **MP3·AAC 원본.** 시간표는 rekordbox 시간축이라 음원 프레임은 `(시각 − predictedOffset) × 샘플레이트`. 곡 머리를 살리면 음수 프레임(인코더 지연)은 무음으로 채워, 출력 WAV의 0초가 rekordbox가 보던 원본의 0초와 같다. 출력은 PCM이라 출력 시간축 = 음원 시간축.
- **큐는 처음 나오는 자리 하나에만.** 같은 소리가 여러 번 나와도 핫큐 슬롯이 겹치지 않고, 인트로를 늘려도 메모리 큐가 또 생기지 않는다. 루프는 끝까지 한 조각 안에 드는 자리로 옮기고, 빠진 구간의 큐·이음새에 걸친 루프는 이유와 함께 버린다. 큐 시각은 ms 정수라 조각 시작 1ms 앞 큐도 그 조각에 든다.
- **곡 넣기는 기존 흐름 그대로.** 추가한 곡(`StagedTrack`)에 추정 대신 변환한 그리드·옮긴 큐 초안과 원곡 정보(태그 초안, 렌더한 WAV에는 태그가 없다)를 둔다(`EditStaging`). 넣기·XML 내보내기는 그 초안을 쓴다.
- **편집 창(`Sources/DJCrate/Edit/`, #128 컷 편집기).** 덱과 따로 된 창(`TrackEditWindow`)에 원곡 줄과 결과 타임라인이 있다. 원곡 그리드·큐·길이는 창을 열 때 덱에서 읽는다. 원곡 파형을 끌면 양 끝을 가까운 마디 줄에 붙여 구간을 고르고(`BarLayout.selection`), 결과의 고른 클립 뒤(없으면 끝)에 넣는다. 클립은 목록 구간 하나(`TrackEdit.clips`, 이어진 구간도 합치지 않음)이며 재생선에서 가장 가까운 마디 줄로 자르기(`TrackEdit.split`)·복제·지우기·끌어 옮기기(`dropOffset`)를 한다. 목록을 바꿀 때마다 창의 `undoManager`에 바꾸기 전 목록을 남겨 편집 메뉴 ⌘Z·⇧⌘Z로 되돌린다. 규칙에 맞지 않는 목록(가운데 곡 머리 등)도 `TrackEdit.place`로 그려 고칠 수 있게 하고 렌더·결과 재생만 막는다.
- **확대·다듬기·끌어 넣기(#134).** 두 줄은 따로 보이는 자리(`EditViewport`: 보이는 길이·왼쪽 끝)를 들고, 그리기·누르기는 모두 그 자리 기준으로 시각을 바꾼다. 보이는 길이를 들고 있어 결과가 늘거나 줄어도 마디 폭이 그대로이고, 가장 가깝게는 2마디다. 확대는 세로 휠·핀치(포인터 자리 기준, 덱 확대 파형과 같은 `WaveformScrollPolicy`)와 `=`/`−`/`0` 키·줄 아래 단추(재생선 기준)로 하며 ⌘+/−(보기 › 글자 크기)와 겹치지 않는다. 재생선이 보이는 자리 오른쪽 끝을 넘으면 다음 쪽으로 넘긴다(다른 곳을 보고 있으면 끌어오지 않는다). 클립 가장자리(5포인트, 좁은 클립은 길이의 ¼)를 끌면 원곡 시각으로 바꿔 가까운 마디 줄에 붙이고(`BarLayout.trimmed`, 곡 머리는 맨 앞·잘린 끝 마디는 맨 뒤 클립만), 손을 뗄 때 한 번에 바꿔 실행 취소 하나로 남긴다. 원곡에서 고른 구간 안을 아래로 끌면 결과 줄 위에서 놓을 자리(`insertion`: 가운데를 지난 클립 수, 곡 머리로 시작하는 결과의 맨 앞은 피함)를 보여 주고 놓으면 넣는다. 옆으로 끌면 예전처럼 새로 고른다.
- **창 재생기(`EditAudioPlayer`).** 덱과 따로 원곡을 메모리에 풀어(`DecodedAudio`) 원곡 줄은 그대로, 결과는 렌더하지 않고 재생한다: `TrackEdit.playbackItems`가 렌더러와 같은 프레임 예약표(조각 본문 + 이음새 앞 4ms 섞기 칸)를 만들고, 본문은 원곡 버퍼를 복사 없이 잘라, 섞기 칸만 `EditRenderer.playbackBuffer`로 만들어 노드 샘플 시각에 잇는다. 그래서 결과 어디서든(이음새 가운데서도) 시작해도 렌더 파일과 소리가 같다(`EditRendererTests`). 멈출 때는 엔진 `stop()`. 이음새 듣기는 앞뒤 2마디만 재생하고 멈춘다. 창의 단축키(스페이스·←→·⏎·⌫·⌘D·⌘B·Esc, `TrackEditCommand`)는 이 창이 앞일 때만 받고, `KeyRouter`는 이 창을 덱 창으로 보지 않는다. 결과는 `DJC_HOME/edits`에 두고 추가한 곡에서 고른다. 렌더는 백그라운드, 작업을 취소하면 조각 사이에서 멈추고 쓰던 파일을 지운다.
- 2026-09-26 확인(`djc lab edit-render --check-grid`, 스냅샷 사본·임시 `DJC_HOME`):
  - MP3(LAME, 192 BPM) 인트로 연장: 조각 영역 샘플이 원본을 처음부터 이어 읽은 값과 차이 0. 출력에서 추정한 박과 변환 그리드의 차이 중앙값 7.0ms = 원본 기준선(원본 추정 vs rekordbox 그리드) 7.0ms.
  - FLAC(168 BPM) 곡 머리 + 이음새 3곳: 샘플 차이 0, 박 차이 0.0ms(기준선 0.0ms).
  - 사본 DB에 넣기(`--into`): 분석 파일에서 다시 읽은 그리드가 보낸 그리드와 1.0ms 안, 큐 16개가 계획한 위치와 ms 단위로 같음.

## 화면 성능

- 재생 중 매 프레임(디스플레이 링크 60Hz) 바뀌는 값은 `playhead` 하나다. 이 값을 읽는 뷰만 매 프레임 다시 그려진다.
- 매 프레임 SwiftUI 갱신 한 번에 창 전체 비용이 든다(프레임당 약 2ms, 릴리스 측정). 그래서:
  - 글자·전체 파형 재생선은 `displayTime`(15Hz)을 읽는다.
  - 레벨 미터는 자체 30fps 타이머 대신 재생 틱이 올리는 `meterFrame`으로 갱신한다.
  - 결과: 재생 중 메인 스레드 366 → 약 215ms/초. 빠른 목록 스크롤 때 25ms 넘는 프레임 약 30 → 10번(3초당).
- 확대 파형 그리기 자체는 약 1ms로 작다. 막대 그리기를 끄는 A/B에서 차이가 없었다.
- 일부 뷰를 별도 NSHostingView로 떼는 방법은 오히려 느렸다(504ms/초).
- 조작별 비용은 `--ui-perf=`로 잰다(#129, 곡 3천·재생 목록 300개 합성 라이브러리). 2026-09-28에 찾아 고친 것:
  - 닫힌 인스펙터도 SwiftUI가 내용을 계속 계산해, 곡을 고를 때마다 태그 입력 칸을 새로 만들고 덱 ScrollView까지 창 레이아웃을 다시 잡았다. 인스펙터가 열려 있을 때만 그린다.
  - `ContentView` 본문은 선택·표시 줄을 읽지 않는다. 창 제목·부제·빈 목록 안내는 작은 수정자·뷰가 읽는다.
  - `pendingUUIDs`는 부를 때마다 합집합을 만든다. 곡마다 거를 때는 한 번 받아 둔다(초안이 많으면 곡 선택마다 수백 ms였다).
  - 결과(릴리스 최적화): 곡 선택 약 55 → 12ms, 태그 초안 600곡일 때 약 290 → 20ms.
- 사이드바 본문(`Sidebar.body`)은 목록 구조(어떤 줄·구역이 있나)만 읽고, 배지·진행 값은 줄 뷰(`SidebarStagedRow`·`SidebarPendingRow`·`SidebarGridJobRow` 등)가 각자 읽는다(#141). 본문이 다시 계산되면 List가 재생 목록 전체를 다시 비교한다. `@AppStorage`를 든 뷰는 부모(ContentView)가 다시 계산될 때마다 값이 바뀐 것으로 보여 본문이 새로 계산되므로(덱에 곡을 올리면 덱 높이가 바뀌어 ContentView가 다시 계산된다), 사이드바는 설정값을 구역 뷰(`PlaylistSection`·`SidebarHistorySection`·`SidebarStatusSections`)에서 읽는다. `--ui-perf=load`의 `OutlineListCoordinator.diffRows` 대부분(곡 하나에 약 55~70ms)은 사이드바가 아니라 덱 큐 목록(`CueRow`)이다.
- 덱 큐 목록(`CueListView`)은 곡이 바뀔 때 큐 id가 모두 달라 행이 통째로 교체된다(#152). 교체 때 표가 행 높이를 자동으로 다시 재던 것(`_doAutomaticRowHeightsForInsertedAndVisibleRows`)을 `CueListFixedRowHeight`가 표의 자동 행 높이를 끄고 28pt로 고정해 없앴다. 결과(릴리스 최적화, `--ui-perf=load` 6곡, Time Profiler 번갈아 3번): `diffRows` 중앙값 370 → 72ms(곡 하나에 약 62 → 12ms), 자동 행 높이 표본 약 360 → 0ms. 남은 몫은 새 행 뷰를 만드는 `viewFor`가 대부분이다. SwiftUI는 행이 교체될 때 표의 `rowHeight`를 `defaultMinListRowHeight`(기본 24pt)로 되돌리므로 List에도 같은 값을 준다. 고정이 걸렸는지(표를 찾았는지)는 `CueListRowHeightTests`가 실제 창에서 확인한다.
- 곡 목록이 바뀔 때(사이드바 항목·정렬·검색, #137) `reloadData`를 쓰지 않는다. 그러면 보이는 셀·행 뷰를 모두 버리고 새로 만든다. 줄 수만 알리고(표 높이 애니메이션 없이) 만들어 둔 줄의 칸을 제자리에서 다시 채운다. 목록 글자 칸(`TrackTextCell`)은 제약 대신 `layout()`에서 프레임으로 둔다. 결과: 재생 목록 전환·정렬 약 175 → 45ms, 검색 지우기 약 200 → 65ms, 전체 목록(3천 곡)으로 전환 약 155 → 95ms.
- 태그 시트 스크롤(#140): 칸마다 `toolTip`을 달면 칸을 다시 쓸 때마다 추적 영역이 생겨, 툴팁은 표(`SheetTableView`)가 영역 하나로 알려 준다. 시트 글자 칸(`SheetCell`)도 제약 대신 `layout()`에서 프레임으로 두고, 초안 표식 뷰는 초안 칸에만 만들며, 색·읽기 값은 상태가 그대로면 다시 쓰지 않는다. 스크롤마다 AppKit이 하위 뷰를 모두 훑으므로 칸당 뷰 수가 비용을 정한다(레이어를 선택·기준 칸에만 두는 시도는 이득이 없었다). 결과(릴리스, 합성 곡 3천): 빠른 스크롤 한 번 약 2.5 → 1.7ms(곡 목록 약 2.4ms), 메인 스레드 일한 시간 약 710 → 580ms/초, 시트 열기 약 175 → 145ms.
- 재생 중 덱 화면(#139, 합성 곡 3천·실제 오디오 엔진, 릴리스 최적화, 전후 번갈아 5번 중앙값): 재생 중 가만히 235 → 138ms/초, 스크럽 315 → 184ms/초, 재생 중 확대·축소 91 → 66ms(6번 합). Time Profiler(`--attach`)로 본 원인 둘:
  - 확대 파형 Canvas가 매 프레임 글자(마디.박·큐 이름·핫큐 칩·다음 큐 알약)를 다시 해석하고 재는 데 `draw` 80ms/초 중 대부분이 들었다. `WaveformTextCache`가 해석한 글자(`ResolvedText`)와 잰 크기를 글자·모양별로 두고 다음 프레임에도 쓴다. 화면 배율·명암·굵은 글자 설정이 바뀌면 비운다. 글자 해석 30 → 2ms/초, `draw` 80 → 29ms/초.
  - 덱 머리 시각(`DeckHeaderTime`)이 초당 15번 바뀔 때마다 덱 `ScrollView`가 크기를 다시 쟀다(`fixedSize`로 감싼 덱 전체, 재측정 약 18ms/초와 호스팅 뷰 크기 요청 약 10ms/초). 폭만 고정한 자리 안에서 글자가 바뀌면 바깥 스택·`ViewThatFits`가 다시 계산되므로, 바뀌지 않는 기준 글자가 자리 크기를 정하고 바뀌는 글자는 그 위에 얹는다(크기 계산에 끼지 않는다). 재측정 18 → 0ms/초. `NSHostingView.layout`에 보이던 시간의 대부분은 레이아웃이 아니라 그 안에서 도는 Canvas 그리기였다.
  - 남은 재생 중 비용은 확대 파형 Canvas 그리기·화면 갱신(그 요소를 숨기면 154 → 74ms/초)과 나머지 화면이다.
- 사이드바·인스펙터를 여닫고 창 크기를 바꾸는 동안(#138) 큰 뷰의 본문이 프레임마다 다시 계산되지 않게 한다. `--ui-perf=`는 조작마다 본문이 계산된 횟수와 메인 스레드 CPU 시간도 찍는다(뷰 `body` 첫머리의 `let _ = PerfProbe.body(Self.self)`가 센다, `--perf-trace-body`는 다시 계산된 이유도 찍는다). 부하가 흔들려도 견줄 수 있는 것은 횟수와 CPU 시간이다. 찾아 고친 것:
  - 이름에 점이 든 설정(`sidebar.visible`·`view.textScale`·`deck.cueListFilter`)을 `@AppStorage`로 두면 KVO로 지켜보지 못해, UserDefaults의 어느 키가 바뀌어도(창 크기를 바꾸는 동안 창 프레임 자동 저장 등) 그 뷰를 다시 계산한다. `ObservedSetting`(같은 키가 실제로 바뀔 때만 알림)으로 둔다. 키 이름·기본값은 `SettingKeys` 그대로다.
  - 덱이 잰 높이(`deckChromeHeight` 등)를 주 창(`ContentView`)이 `@State`로 들면, 창 폭이 바뀔 때마다 컨트롤 줄바꿈으로 덱 높이가 바뀌어 툴바·사이드바·메뉴까지 본문을 다시 계산한다. 본문(덱·목록)은 `LibraryDetail`이고 잰 크기 상태는 거기서 든다. 파형 높이 메뉴는 그 값에서 나오므로 포커스 값 `\.waveformHeight`로 따로 싣는다.
  - 덱의 큐 목록 폭 단계(`DeckWidthClass`)는 본문이 진짜 크기만 걸러(`DeckLayout.isDetailMeasurement`) 재서 덱에 넘긴다. 덱이 자기 폭을 재면 SwiftUI가 창 최소·최대 크기를 알아보려고 제안한 임시 폭에도 상태가 바뀐다. PR #151의 고정 헤더 배치는 유지한다.
  - `FlowLayout`은 칸의 자연 크기를 캐시에 재 두고 제안 폭마다 줄을 나눈다. 칸 내용·개수가 바뀌면 SwiftUI가 캐시를 갱신하며, PR #151의 양끝 맞춤·세로 가운데 정렬도 같은 크기를 쓴다.
  - 파형 높이에 쓰는 `fittedChromeHeight`는 곡이 있고 본문 높이가 1pt 넘게 바뀔 때만 갱신한다(PR #151). 곡 로드·덱 내용 증가만으로 파형 높이를 줄이지 않고 덱 뷰포트만 제한한다.
  - 2026-09-30 재검증: PR #151·#139·#152가 포함된 `a365937`과 수정본을 같은 `UIPerfFixtureCapture` 합성 라이브러리·가짜 오디오·디버그 빌드로 교대 A/B(예열 1쌍 제외, 5쌍 중앙값)했다. 폭 1700→1415→1700의 40단계에서 메인 스레드 CPU 5234→1868ms, 단계 실행 시간 67.5→24.1ms, 본문 계산은 `ContentView` 152→0·`DeckView` 304→2·`CueListView` 304→0이었다. 사이드바·인스펙터 각 8회 여닫기의 CPU 개선은 2.0%·3.8%로 작았다. 수정 뒤에도 최대 프레임 간격은 각각 93.3·85.0·221.9ms로 지연이 남는다. 실제 마우스 끌기·오디오 재생·릴리스 성능은 이 측정으로 확인하지 않았다.
  - 같은 합성 곡·라이트/다크·글자 배율 1.0/1.3/1.5로 캡처했다([대표 전후 화면](images/issues/138)). 넓은 창의 배치는 같고, 좁은 창에서 임시 본문 높이 0pt가 끼어 파형이 80pt로 줄던 문제는 실제 크기만 받아 요청한 150pt를 유지한다. 요청 높이 480pt·실제 창 높이 변경도 별도 회귀 시험으로 확인했다.

## 글자 크기

- macOS는 Dynamic Type을 지원하지 않아(`dynamicTypeSize`를 바꿔도 글자 크기가 그대로다) 앱이 글자 배율을 직접 곱한다. 배율은 `SettingKeys.textScale`(1·1.15·1.3·1.5배, 규칙은 `TextScale`)이고 보기 › 글자 크게·작게(⌘+ · ⌘−)와 설정 › 일반에서 바꾼다.
- 창마다 `AppTextScale`이 배율을 환경값 `textScale`로 넣는다. SwiftUI 글자는 `Font.scaled(.caption, scale)`(1배면 텍스트 스타일 그대로), 고정 pt(CDJ 패드)는 `Font.scaled(size:…)`, 파형 Canvas는 `WaveformMetrics`, AppKit 표(곡 목록·태그 시트)는 `NSFont` 크기와 `rowHeight`에 곱한다. 1.3배부터는 작은 컨트롤을 한 단계 키운다.
- 가장 작은 글자는 10pt(macOS 최소)다. 파형 눈금처럼 자리가 모자라면 글자를 줄이지 않고 라벨 수를 줄인다(`BeatRulerLabel`).

## USB

형식·절차는 `docs/usb-internals.md`, USB 코드를 고칠 때 규칙은 `.claude/rules/usb-write.md`.

- **한 모델, 두 형식**: USB 라이브러리를 곡·재생 목록·큐 모델 하나로 읽고, 쓸 때 그 모델에서 OneLibrary(`exportLibrary.db`)와 Device Library(`export.pdb`·`exportExt.pdb`)를 따로 만든다(`UsbFormat`). 두 형식이 같은 내용을 담도록 계획은 한 곳에서 세운다.
- **내보내기 흐름**: 후보(`UsbExportCandidates`, 스냅샷 사본·share 읽기만) → 계획(`UsbExportPlanner`, DJCDomain 순수: 경로·ID·막힘·확인 안 된 규칙) → 빌더(`UsbLibraryBuilder`, 계획 → 두 형식 모델, Device Library 행 크기로 막힌 곡은 빼고 다시 계획) → 준비(`UsbExportAssembly`, Mac 준비 폴더에 DB 셋·분석 파일·아트워크를 만들고 변경 묶음을 냄) → 쓰기(`UsbWriter.write`) → 검증(`OneLibraryVerifier`·`PdbVerifier`·`UsbInvariantVerifier`, USB에서 다시 사본을 떠서). 이 순서를 한 번에 부르는 것이 `UsbExportSession`(DJCStorage)이고 CLI `djc usb-export`와 앱이 쓴다. 세션은 넘겨받은 스냅샷 사본을 세션 전용 폴더에 한 번 더 떠서 읽고 끝나면 지운다(사용자 스냅샷 폴더는 건드리지 않는다).
- **옮기기 흐름**(Device Library만 있는 USB → OneLibrary 더하기): USB DB 사본 → pdb 모델 → 변환(`UsbMigration.model`, OneLibrary 몫만 채우고 Device Library 투영은 그대로) → 준비(새 `exportLibrary.db`, b 아트워크 = a 사본) → 쓰기(`UsbWriter.write`, 검사기 `UsbMigrationInspector`). 원래 파일은 바꾸지 않고 목표 지문에 원래 pdb 해시를 넣어 G 단계가 확인한다. 이 순서를 부르는 것이 `UsbMigrateSession`(DJCStorage)이고 CLI `djc usb-migrate`와 앱 USB의 “OneLibrary 더하기…”가 쓴다. 앱은 `UsbWriteCoordinator`의 잠금·미리 보기·확인·쓰기·다시 읽기·회복 흐름을 타고, 옮기기 백업으로 되돌릴 수 있다(그 뒤 다른 쓰기가 성공하면 이전 백업 메뉴는 숨긴다). 규칙은 `docs/usb-internals.md` §8.4.
- **파일 먼저, DB 마지막**: 음원·분석 파일·아트워크를 먼저 쓰고 라이브러리 DB를 마지막에 바꾼다. 중간에 멈춰도 기기는 옛 DB를 읽어 없는 파일을 가리키지 않는다. 새 파일은 임시 이름(`.djc-part-…`)으로 쓴 뒤 이름을 바꾼다.
- **저널은 Mac에**: 쓰기 전 백업과 진행 기록(저널)은 USB가 아니라 DJCrate 데이터 폴더(`usb-sessions/`)에 둔다. USB가 뽑혀도 회복할 근거가 남는다.
- **쓰는 길은 하나**: `UsbWriter.write`만 USB에 쓴다(막힘 확인 → Mac 백업 → 파일 → DB 교체 → 지우기 → 검증, 실패는 백업으로 되돌림). 형식을 모르는 변경 묶음(`UsbChangeSet`)을 받고, 형식별 막힘·검증은 `UsbWriteInspector`·`UsbWriteVerifier`로 주입한다. 되돌리기(`restore`)와 회복(`recover`)도 같은 확인을 먼저 거친다. 파일 연산은 `UsbFileSystem` 프로토콜 뒤에 있어 시험이 실패·끊김·분리를 흉내 낸다.
- **회복은 대상 먼저**: 끊긴 쓰기는 USB의 DB 해시로 방향을 정한다(마저 쓰기·되돌리기, 기기가 바꿨으면 다시 계획). 단계마다 볼륨이 아직 붙어 있는지 보고, 사라졌으면 되돌리지 않고 멈춘다(떼어진 마운트 지점 폴더에 쓰면 Mac에 쓰게 된다).
- **USB 위에서 SQLite를 열지 않는다**: USB의 DB는 Mac 사본에서 열고 고친 뒤 완성된 파일을 복사한다. FAT 위에 WAL·잠금 파일을 만들지 않고, 쓰다 뽑혀도 DB가 반쯤 바뀐 채 남지 않게 한다.
- **`._*` 파일**: macOS는 FAT에 확장 속성을 `._이름` 파일로 남긴다. 비교·지문에서는 세기만 하고, 임시 이름은 이 모양과 겹치지 않게 짓는다(`UsbLayout.tempName`).
- **실물 쓰기는 코드 상수로 닫힘**: `UsbPhysicalWriteGate.buildEnabled`가 false인 동안 실물 USB에는 쓰지 않고 디스크 이미지로만 시험한다. 이 동안은 볼륨 정보(가드)와 무관하게 루트가 임시 폴더 아래 마운트 지점이어야 한다(가드 값 하나가 틀려도 실물에 닿지 않게). 열린 뒤에도 쓰기 금지 목록(fail-closed)·허용 목록·`--confirm` 볼륨 이름을 거친다. 확인하지 않은 규칙(`UsbProvisionalRule`)이 필요한 계획은 실물에 쓰지 않는다.
- **볼륨 정보는 DiskArbitration으로**: 디스크 이미지 판정·FAT32 판정은 DA 설명 사전 + statfs + `hdiutil info` 짝을 순수 함수(`UsbVolumes.make`)로 합쳐 정한다. 모르면 실물·FAT32 아님으로 본다.
- **앱은 사본으로 읽기만**: 사이드바 USB 절은 `UsbStore`(모양·라이브러리·갱신 상태)가 `UsbHost` 프로토콜 뒤의 호스트로 읽는다. 실제 호스트(`SystemUsbHost`)는 `UsbVolumeMonitor`(DA 나타남·경로 바뀜·사라짐, 해석은 순수 함수)로 볼륨을 지켜보고, 읽기(`UsbRead.info`·`UsbRead.library`, DJC_HOME의 `usb-snapshots/<볼륨키>/` 사본)와 꺼내기는 메인 액터 밖에서 한다. 쓰기 금지 목록 판정(`UsbRead.readRefusal`)이 모양 판정·사본 뜨기보다 먼저라, 목록에 있거나 목록이 없는 실물 볼륨은 사본도 뜨지 않는다. 읽기 직전에는 그 자리의 볼륨을 다시 보고(`UsbRead.currentVolume`) 새 정보로 판정한다 — 훑은 뒤 같은 자리에 다른 볼륨이 붙어도 옛 정보(디스크 이미지·UUID)로 지나가지 않게. 시험 실행(`UsbReadPolicy.diskImagesOnly`: 디버그 빌드 + `DJC_HOME`·`--usb-selftest`)은 디스크 이미지만 본다.
- **앱 내보내기**: 빈 FAT32 볼륨의 "USB로 내보내기…" → 시트(`UsbExportSheet`: 형식·원본 목록 트리·고른 곡·미리 보기) → `UsbWriteCoordinator`(rekordbox·Agent 꺼짐 → 볼륨 잠금 `UsbStore.beginWrite` → `UsbExportSession` 미리 보기 → 확인 창 → 쓰기, DB 교체 전까지만 취소 → 토스트 [꺼내기]). 세션·`UsbWriter` 호출은 `UsbWriteService` 뒤에 있어 시험이 가짜로 바꾸고, 모두 메인 액터 밖에서 부른다. 끝나지 않은 저널(닫힌 상태가 아닌 것)이 있는 볼륨이 나타나면 알림만 띄우고, 회복·되돌리기는 사용자가 누를 때만 한다(되돌리기는 저널을 회복으로 닫은 뒤 그 쓰기의 백업으로 `restore`, 기기 변경이 있으면 한 번 더 묻는다). 디버그 자가 테스트 `--usb-selftest`가 디스크 이미지로 이 흐름을 지난다.
- **앱 USB 편집은 초안으로**: 곡 목록의 "USB에 넣기 ▸ <볼륨> ▸ 컬렉션·목록", 사이드바 USB 컬렉션·목록에 끌어다 놓기, USB 곡의 "USB에서 빼기"·"‘목록’에서 빼기", 목록 만들기·이름·지우기·순서, "로컬 변경을 USB에 반영"(갱신 가능 곡만, 곡마다 로컬에서 바뀐 부분만 — 바뀐 부분이 같은 곡끼리 편집 하나)은 모두 볼륨키별 초안(`UsbDraftStore`, DJC_HOME의 `usb-drafts/`)에 편집을 더할 뿐이다(`UsbEditActions`, 파일 입출력은 메인 액터 밖). 초안 고치기(더하기·빼기·버리기)와 초안 쓰기는 볼륨마다 한 줄(`UsbStore.draftQueue`)로 서서 겹쳐도 편집을 잃거나 순서가 바뀌지 않는다. 처음 편집 때 base 지문은 사이드바 읽기처럼 그 자리의 볼륨을 다시 보고(`UsbRead.currentVolume`) 쓰기 금지 목록을 지난 뒤에만 뜬다(못 뜨면 빈 base, 쓸 때 다시 계획). 목록 위로·아래로 옮기기는 초안의 목록 편집을 적용한 자리에서 세고, 이어 누르면 한 편집으로 고치며 제자리로 돌아오면 뺀다. 더하기 전에 읽은 라이브러리·볼륨만으로 가볍게 막힘을 판정해(쓰기 계획과 같은 문구, 실물 관문은 임시 폴더 밖 디스크 이미지도) 막힐 편집은 메뉴(순서·로컬 변경 반영 포함)를 막고 이유를 도움말로 단다. 쓰기 금지 목록 볼륨에는 초안 메뉴가 없다. 초안이 남은 채 빠진 볼륨은 이번 실행 동안 사이드바에 "연결 안 됨"으로 남아 초안을 더·빼·버릴 수 있고 쓰기만 막힌다. 쓰기는 사이드바 "USB 쓰기 대기"(`UsbPendingView`)의 "USB에 쓰기…" 하나로, 내보내기와 같은 `UsbWriteCoordinator`·`UsbWriteService`(`UsbEditSession.preview`·`writeDraft`) 흐름과 잠금·회복을 탄다. 미리 보기는 초안 줄 밖이라, 쓰기 줄에 선 뒤 초안이 확인 창에서 본 편집과 다르면(미리 보는 동안 더하거나 뺌) 쓰지 않고 지금 초안으로 다시 미리 보고 묻는다(확인한 편집만 쓴다). 로컬 사본은 앱이 연 스냅샷 사본을 넘기고 세션이 곡 더하기·갱신 때만 `local-<세션>/`에 따로 뜬다(앱 USB 코드는 스냅샷을 뜨거나 정리하지 않는다). 쓴 뒤 초안에는 막힌 편집만 남는다.
- **USB 목록은 읽기 전용**: USB 곡은 곡 목록(`TrackTable`)에 `usb:<볼륨키>:<content_id>` ID의 줄로 보이고, 편집·쓰기·재생 목록·끌기·덱 불러오기 대상에서 빠진다(`LibraryStore.uniqueTracks`). 갱신 상태는 앱이 연 로컬 스냅샷 사본에서 읽은 짝짓기 키(`LocalLibraryKeys`)와 `UsbTrackMatch`·`UsbSyncStatus`로 정한다. USB 목록은 # 번호·제목·아티스트·BPM·키·갱신 상태 칸만 보이고(들어가기 전 칸 배치는 저장하지 않고 나올 때 돌린다), 읽지 않은 큐·그리드 칸은 비운다. USB 코드는 로컬 스냅샷을 뜨거나 정리하지 않고, 명시한 사본(`--db`·`DJC_DB`)으로 연 창은 사본 폴더(`DJC_REKORDBOX_DIR`)가 없으면 라이브에서 스냅샷을 뜨는 길(스냅샷 뜨기·창 복귀·곡 추가·빼기 미리 보기·복원 전 확인)을 모두 막는다(`LibraryStore.snapshotTakeAllowed`).
